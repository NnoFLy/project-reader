# Keep file authority in Core and editing in Notes

Core is the sole authority for file identity, read/create/write, rename/move, delete/trash/restore, source access, shared folders/tags/pins, and open dispatch. Reuse and migrate Library's existing VFS authority behind Core, preserving data, behavior, and writer fencing without assuming an IndexedDB rewrite. We chose this over a competing Notes store to avoid divergent identities, metadata, permissions, and conflict policies. Plugins consume Core contracts and cannot bypass or change generic file rules. Library retains browsing and import/relink workflows through Core.

Notes owns standalone `.md`/`.org` editing. Viewer retains books, reading sessions, durable reading state, and document-bound passage/region annotations under [ADR-0001](0001-viewer-owned-reading-workspace.md). Note files remain distinct from those annotations and their Note drafts. This decision does not introduce a generic host workspace or mixed editor/reader tabs. Issue #54 retains reader-format concerns; Notes does not depend on completion of every additional format.

Saving depends on the source. Managed files save through Core; linked files write to their originals through Core with explicit permission where platform access supports it. Unsupported workflows offer an explicit managed import, never a silent mode switch. Unavailable linked sources may retain recoverable pending-source edits without guaranteeing external access. Local recovery is not a completed source save, and failures must retain text without reporting success. Detected external changes require manual compare/reload/keep-both resolution before replacement. Unlinking never deletes the original.

Folders, tags, and pins are shared Core metadata; storing them must not rewrite Markdown frontmatter or Org properties. Complete export carries files, attachments, structure, and metadata for portable reconstruction; unavailable linked content must be reported, not silently omitted. Raw file export omits app-only metadata. Export round-trip validation does not prescribe a backup-restore interface or full version history. Browser eviction or cleared site data can remove local content; autosave is not backup.

This is accepted direction, not implemented capability. The [Notes specification](https://github.com/NnoFLy/project-reader/issues/76), [Core prerequisite](https://github.com/NnoFLy/project-reader/issues/77), and [Notes editor issue](https://github.com/NnoFLy/project-reader/issues/78) hold requirements and gates. Before implementation, validate hands-on flows, migration and failure contracts, and editor/source-access feasibility on real iOS Safari and Android Chrome. The trust boundary includes untrusted content, URLs, attachments, external paths, and backup input. Implementation must sanitize previews, reject scripts/active unsafe HTML/unsafe URL schemes, bound parsing/indexing, validate permission-bound writes and backup input, and prevent automatic upload/tracking.
